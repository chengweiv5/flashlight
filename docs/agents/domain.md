# Domain docs：单上下文

本项目采用单上下文领域文档布局，不预建多上下文目录。

## 按需读取

在探索领域模型、讨论术语或作架构决策前：

1. 通过根目录 [README.md](../../README.md) 找到当前产品设计，区分已确认范围、待验证能力与已实现行为。
2. 若根目录已有 `CONTEXT.md`，读取与当前问题相关的术语及约束。
3. 若已有 `docs/adr/`，读取与当前改动相关的架构决策记录。

`CONTEXT.md` 或 `docs/adr/` 尚不存在时继续工作，不将其缺失本身当作问题，也不为填满目录创建空文档。术语或决策实际明确后，再按需建立对应文档。

## 布局约定

以下表示文档职责，并不声称所有文件已存在：

- `CONTEXT.md`：唯一的项目领域上下文、术语和关键约束。
- `docs/adr/NNNN-<decision-slug>.md`：已作出的架构决策、原因、权衡与后果。
- `docs/superpowers/specs/`：经审阅的产品／设计规格；草稿应注明其状态。
- `design/flashlight-v<完整版本号>.pen`：UI 正式设计源，遵循根目录 [AGENTS.md](../../AGENTS.md) 的版本快照门禁。

不因存在手电筒与柔光灯两个模式就拆出两个领域上下文。若未来确需多上下文，先明确边界并经确认后更新本约定。

## 术语与事实边界

- 已有 `CONTEXT.md` 时，问题标题、设计、测试和代码命名使用其中的术语，不随意替换成存在歧义的同义词。
- 尚无术语表时，以当前已确认的产品设计为准；术语缺口按实际需要澄清。
- 设备能力、设计意图和实现结果分别记录。计划支持不等于系统已支持，也不等于功能已通过真机验收。

## 架构决策冲突

提议与现有 ADR 冲突时，指出对应 ADR、冲突内容及重新讨论的原因，不能静默覆盖。

新决策经确认后记录；被取代的历史决策保留并标明替代关系，不篡改历史使其看似一直一致。
